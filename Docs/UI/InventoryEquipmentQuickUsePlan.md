# Inventory equipment and quick use implementation plan

Implement the [equipment and quick-use spec](InventoryEquipmentQuickUseSpec.md) in `AtmosphericScrubberEncounter`. Use the current three-column inventory prefab as the starting point. Preserve the pending inventory assets, their GUIDs, and the existing scene layout. Enable the new flow through the Scrubber runtime configuration so Wakeup and other scenes retain their existing hotbar flow until rollout is approved.

## 1. Add run-owned equipment and quick-use state

**S1–S5.** Add one run-owned record for the Weapon item ID, Tool item ID, active equipment slot, and pinned consumable ID. Put commands to equip, unequip, switch, pin, and clear behind the existing application/container boundary. Read eligibility from authored tags and supported item capabilities. Validate references against carried inventory and reconcile when its contents change. When the same item remains carried, moving or merging its stack preserves the assignment. The view reads this state and sends commands.

Check empty and occupied slots, invalid or missing items, the wrench qualifying for either slot, independent pin changes, and fallback when the active item leaves inventory. Verify that a stack move preserves the active item and removing the last copy clears it.

## 2. Persist the state and migrate existing saves

**S7–S9.** Extend `SaveGameData`, `SaveJsonCodec`, and `ContainerSaveSession` capture and restore. Take the existing startup and recovery path through `GameCompositionRoot` and `SaveGameService`. Choose the equipment flow at run startup, before registering the player containers. Keep migration gated to the updated flow so a scene using the legacy flow can still read its hotbar inventory.

For an existing save, resolve legacy item IDs, retain carried slot positions, and merge or place legacy hotbar stacks under the existing stack limits. Put any remainder in migration overflow within carried storage. Make overflow visible in Inventory and eligible as a source for equipment, use, and transfers out. Exclude it from pickup capacity and ordinary transfer destinations. Consume or transfer its contents through the existing command service and retire the overflow when empty.

The current save schema stores hotbar contents but has no saved selected index. Migrate those saves by choosing the first eligible hotbar item in slot order, preferring Weapon for dual-purpose items. Publish the equipment state, carried storage, and removal of the legacy hotbar contents in the same durable snapshot. Use the existing atomic save and recovery path. Update `StartingLoadoutCoordinator` and the authored loadout for the new flow so the configured wrench is granted to carried inventory and equipped in Weapon once, before readiness. Include the new state in new-run and survivor lifecycle handling under the existing ownership rules.

Extend the focused codec, starting-loadout, and persistence checks. Cover legacy saves with room, partial stacks, full inventory, and no eligible item. Compare item totals and IDs. Inject a write failure, reload or retry, and verify that a complete old or new snapshot survives without a second grant. Confirm the legacy-flow load path retains its hotbar contents.

## 3. Wire Primary, Switch Equipment, and Use

**S2–S6.** Adapt `EquippedItemView` and `PlayerItemActionComposition` to resolve Primary from the in-hand item in the updated flow. Keep combat ownership and stale-action checks. Use equipment identity and lifetime to invalidate an active action when the player switches away or loses the item. A carried-slot revision change alone should leave a swing valid when the same item stays equipped.

Adapt `SelectedVitalItemUseCoordinator` and `PlayerVitalsComposition` to resolve the pin to the first matching occupied carried slot and use the existing revision-checked consumable transaction. Add Switch Equipment to the shared input asset and generated wrapper. Check existing bindings before choosing keyboard and controller defaults, then route the action through `UnityInputHost` and `SceneBindings` with the same modal, held-input, and teardown protections as Primary and Use. In the updated flow, replace the gameplay number-key selection path with this switch action.

Run the affected equipment, vital-use, and real-input checks. Cover switching during windup, depletion across multiple stacks, rejected effects, unchanged equipment on Use, held buttons across modal transitions, and contextual interaction remaining available.

## 4. Update the prefab and verify the player journey

**S1, S4, S6–S9.** Update `InventoryScreenView` and the authored Inventory prefab with Weapon and Tool rows, Equip and Unequip, and Pin and Clear. Show a destination choice for dual-purpose items and distinguish the item in hand from the inspected item. Remove the hotbar dock, numbered strip, and Assign shortcut from the updated scene. Keep carried-item rearrangement. Use the existing HUD to show the item in hand and the pinned consumable with current quantity and device hint. Update `InventoryScreenAuthoring` and `ScrubberEncounterBuilder` so regeneration preserves the intended prefab and scene wiring. Check both the saved scene and the builder path.

At 1920×1080 in the actual Scrubber scene, run a new game, swing the wrench, equip and switch to a second eligible item with Inventory closed, pin and use a consumable, rearrange carried items, and reopen Inventory. Use test-only item data for the second slot if needed. Verify keyboard and controller navigation, HUD restoration, empty and full inventory states, and that registered input and view listeners release on scene exit. Exercise reload and scene return with a controlled save store so the normal disposable demo behavior is preserved. Keep evidence tied to the tested source and prefab revisions. Run only the directly affected suites and scene journeys.

## Research findings that affect implementation

1. **The Scrubber demo cannot qualify reload persistence as authored.** `RestorationDemoSession` uses a fresh in-memory store, and `GameCompositionRoot.BindScene` resets disposable player state on scene binding. Use the demo for the player-facing journey. Qualify reload, scene return, and interrupted writes through a production-session test fixture or a controlled harness of the same composition path, with isolated saves. Keep the demo's reset behavior and test it separately. [Demo store](../../Assets/_Project/Features/World/Restoration/Demo/RestorationDemoSession.cs), [scene binding](../../Assets/_Project/Core/Composition/GameCompositionRoot.cs).
2. **Overflow needs rules in the command service.** Containers save occupied indices, register with an explicit capacity, and filter by item rather than by destination slot. Simply adding slots would make them available to grants and transfers. Track the normal-slot boundary separately from the temporary overflow extent, derive the needed extent from saved contents before binding, and enforce receive restrictions in commands. A different-item swap out of overflow would put the displaced item back into overflow, so reject that swap. Allow transfer into an empty normal slot, partial merges under the normal stack limit, and consuming items in overflow. Test actual pickup and transfer commands against these restrictions. [Container save data](../../Assets/_Project/Domain/ContainerSaveData.cs), [command service](../../Assets/_Project/Domain/ContainerCommandService.cs).
3. **Save before readiness and reconcile after a complete container command.** The command service installs all affected slot arrays before notifying observers, and marks itself busy during notifications. Reconcile against the final carried contents so a move does not briefly unequip an item. A notification may refresh presentation, but must not reenter a guarded session write. Make the equipment record and container contents consistent at capture, including after depletion. Migration must follow backup recovery and persist once before readiness. Preserve the existing schema migration and alias resolution, and distinguish an intentionally empty new equipment record from a legacy save awaiting conversion. [Command publication](../../Assets/_Project/Domain/ContainerCommandService.cs), [session capture](../../Assets/_Project/Domain/ContainerSaveSession.cs), [save recovery](../../Assets/_Project/Application/Persistence/SaveRecovery.cs).
4. **Succession still requires a hotbar binding.** `SurvivorSuccessionComposition` validates both owners and prepares a two-container handoff. For this rollout, keep an empty internal legacy hotbar binding if needed by that contract. Test that all carried contents, including overflow, reach the recovery container and that the departing survivor's equipment and pin clear with the handoff. No item action resolves from that internal binding in the updated flow. [Succession composition](../../Assets/_Project/Features/Player/Succession/SurvivorSuccessionComposition.cs).
5. **Existing item services can be reused, with one change to combat identity.** `ItemCapabilityCatalog` exposes authored tags and Primary or Contextual actions. `PlayerItemActionComposition` already cancels its runner when its equipment view reports a change, but the current view versions the selected hotbar address. In the new flow, version the effective in-hand assignment and actor lifetime. Continue using a fresh revision-checked slot address for consumable use, where the command actually removes a unit. [Capability catalog](../../Assets/_Project/Features/Items/Database/ItemCapabilityCatalog.cs), [equipment view](../../Assets/_Project/Application/Items/EquippedItemView.cs), [consumable coordinator](../../Assets/_Project/Application/Vitals/SelectedVitalItemUseCoordinator.cs).
6. **The current prefab does not offer a visible Move command.** The enabled distilled layout hides Move and Assign, so the revised layout needs an explicit carried-item Move operation reachable with keyboard and controller. Reuse its existing destination and cancellation flow. For Switch Equipment, `Q` and the gamepad left shoulder are candidate defaults with no matching binding paths in the current shared asset. Verify they work through the real input map before finalizing them. [Inventory view](../../Assets/_Project/Systems/Containers/Views/InventoryScreenView.cs), [input asset](../../Assets/_Project/Core/Input/SOLITUDE_InputActions.inputactions).
