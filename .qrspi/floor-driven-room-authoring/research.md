# QRSPI Research: floor-driven-room-authoring

## Answers

### What current room-authoring behavior separates stable room identity, painted occupancy, generated visual floors, and generated architectural boundaries, including adjacent rooms with the same style?

`ShipRoomAuthoring` serializes `roomId`, style, occupancy Tilemap, generated-output reference and one diagnostic string separately. Initialization refuses replacement of an existing identity (Assets/_Project/Features/World/RoomAuthoring/ShipRoomAuthoring.cs:11–31). Creation uses a new GUID, unit Grid, separate inactive `EditorOnly` occupancy child and owned output child (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringCreation.cs:21–39). Occupancy is read using HasTile, independently of marker sprite/style (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringOperations.cs:52–57). Generated floor and sprites are rebuilt from those cells (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomGeometryWriter.cs:18–37). Adjacent same-style rooms retain distinct IDs/maps/outputs in the creation test (Assets/_Project/Tests/Editor/RoomAuthoringCreationTests.cs:34–46). Overlap validation compares world cell positions across rooms, without merging by style (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringValidator.cs:32–43).

### What existing style configuration or serialized asset-to-role mapping identifies available floor, wall, cap, and corner assets, and what dimensions, slicing, pixels per unit, pivots, transparent padding, and import settings determine their usable structural spans and anchors?

`RoomStyleDefinition` maps a floor TileBase, north-wall module array, west/east/south caps, four directional corners and four pairs of boundary reservations. Each module stores sprite, canvas pixels, structural repeat, anchor measured from imported rectangle bottom-left, and pixel offset; PPU constant is 32 (Assets/_Project/Features/World/RoomAuthoring/RoomStyleDefinition.cs:10–38). Validation requires native 32x32 sprite Tile floor, identity Tile transform, 32x64 or 64x64 north canvases with 32/64 repeat, 32x32 caps/corners, 32 PPU and Point filtering (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringValidator.cs:49–85).

No serialized production style mapping was found by `roomId:|styleId:|northWalls:|northReservationsPixels:` search in Assets/_Project .asset/.unity/.prefab sources. Existing test styles are synthesized from opaque white textures (Assets/_Project/Tests/Editor/RoomAuthoringTestFixtures.cs:18–37), or temporary imported PNG assets (Assets/_Project/Tests/Editor/RoomPersistenceTests.cs:18–51).

Existing shared wall/floor assets have other import conventions: Wall_Tilesheet PNG is multiple-sprite, 128 PPU, filterMode 1, compression 1, with 128x128 centered slices (Assets/_Project/Art/Tiles/Walls/Wall_Tilesheet.png.meta:38–80,118–126); its Tile references sprite GUID 701a5fbe7f4554b22995c477ee246fc5 and has collider type 1 (Assets/_Project/Art/Tiles/Walls/Tilemap/Wall_Tilesheet_0.asset:15,36). Floor_Tilemap Tile likewise references a sliced source sprite (Assets/_Project/Art/Tiles/Floors/Tilemap/Floor_Tilemap_0.asset:15). Named Aseprite sources record Point filter but 100 PPU: wall_top has 128x64 rect and pivot (0.5,-1.328125), wall_right 64x128 and pivot (0.5,0), wall_top_right 128x128 and pivot (0.5,0), floor_1 128x128 and pivot (0.5,0) (corresponding Assets/_Project/Art/Tiles/{Walls,Floors}/Sprites/*.aseprite.meta:39,56,130–141). These metadata values do not establish opaque pixel spans, transparent padding or compatible structural anchors. No pixel-content measurements or rendering were performed.

### Which scene-composition, movement, interaction, door, collision, and rendering dependencies consume room geometry or Tilemaps, and which serialized references and behavior must the authoring changes preserve?

Room output writer adds only Tilemap/TilemapRenderer floor and SpriteRenderer architecture; no collider components (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomGeometryWriter.cs:22–37). Runtime succession checks active same-scene Tilemaps without Collider2D as floor, using WorldToCell/HasTile; landing also queries solid colliders excluding triggers and the player's own Rigidbody (Assets/_Project/Features/Player/Succession/SurvivorAvatarAdapter.cs:65–90). Occupancy is hidden on Awake in play and on save/play transition; build strips its object (Assets/_Project/Features/World/RoomAuthoring/ShipRoomAuthoring.cs:34–37; Editor/RoomAuthoringEditLifecycle.cs:17–34,48–55).

Existing start-room composition uses separate floor/north/perimeter maps, explicit wall BoxColliders, a door SpriteRenderer/blocker, interaction trigger/sensor, completion trigger, existing player/input prefabs, systems, and camera (Assets/_Project/Features/World/SolitudeStart/Editor/SolitudeStartBuilder.cs:70–125). Door serializes visual/frames/blocker/accessGate and toggles blocker only when opening completes (Assets/_Project/Features/World/SolitudeStart/SolitudeSlidingDoor.cs:10–17,31–50). Scene serialized blocker remains an explicit fileID reference (Assets/_Project/Features/World/SolitudeStart/Scenes/SOLITUDE_Start.unity:649). Interaction sensor registers/unregisters via trigger callbacks (Assets/_Project/Systems/Interaction/Core/InteractableProximitySensor.cs:23–45); PlayerMovement requires BoxCollider2D and delegates input to MovementBehavior (Assets/_Project/Features/Player/Movement/PlayerMovement.cs:5–12). Searches for Tilemap/HasTile/WorldToCell in Core, Systems and Features C# located succession and start-room authoring consumers, not a general runtime room-geometry service. Existing references and physics/interaction objects are separate from the room generated root.

### What existing Grid transforms, cell sizes, sprite-density conventions, pixel-perfect settings, and rendering-order rules constrain placement of floors, walls, caps, corners, and the player?

Safety checks require unrotated, unit-scale, integer-aligned XY room transform, z=0, unit rectangular Grid with zero gap/XYZ swizzle, and aligned direct occupancy/output children (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringOperations.cs:65–87). Module positions use `origin + (sprite.pivot - AnchorPixels + OffsetPixels)/32f`; spans use 32 pixels/cell (Generation/RoomPlacementBuilder.cs:42–48,62–65). Floor tileAnchor is sprite pivot/32, floor sortingOrder 0 and architecture 1 (Editor/RoomGeometryWriter.cs:25–36). Start-room maps use orders 0/1/2, door 5, player z=-0.1; camera uses 32 assetsPPU and 320x288 reference resolution (Assets/_Project/Features/World/SolitudeStart/Editor/SolitudeStartBuilder.cs:72–74,97,111,123). Saved scene confirms 32 PPU/320x288 and unit Grid (Assets/_Project/Features/World/SolitudeStart/Scenes/SOLITUDE_Start.unity:369–371,2053). A separate OpeningSlice depth sort sets order to 1000-round(y*32), showing a distinct existing rendering rule (Assets/_Project/Features/World/OpeningSlice/OpeningDepthSort.cs:9).

### What existing placement rules and native-pixel rendered evidence establish compatible structural spans, anchors, seams, and baselines for available architectural assets along straight boundaries and at convex and concave corners?

Current straight placement reserves start/end pixels, requires exact divisibility by a single repeat width per side, cycles north module variants and uses bottom-left pixel anchor/pivot compensation (Assets/_Project/Features/World/RoomAuthoring/Generation/RoomPlacementBuilder.cs:33–48,62–65). It places four configured corners at rectangular bounds vertices (same file:51–57), and validates north-wall anchor.y == offset.y so its bottom aligns to north boundary (Editor/RoomAuthoringValidator.cs:59–64). Tests establish arithmetic coverage for 32/64 repeats and a 0.875-unit compensated anchor (Assets/_Project/Tests/Editor/RoomPlacementTests.cs:10–35).

Native-pixel rendered evidence for seams, artwork baselines, transparent padding or convex/concave compatibility is unresolved. The fixture uses solid-white generated sprites (Assets/_Project/Tests/Editor/RoomAuthoringTestFixtures.cs:29–37), not production architectural pixels; placement tests assert positions, not rendered seams. Runtime placement rejects nonrectangles (Generation/RoomPlacementBuilder.cs:29). Review/evidence directories were excluded by the envelope and no render was run; no visual compatibility claim follows from these tests.

### How do current editing and rebuild paths batch changes, record Undo, restore generated content, mark scenes dirty, and persist authored occupancy and room identity through scene save and reload?

PaintCell records occupancy and SetTile then immediately rebuilds each sample; PaintBox records occupancy once and calls SetTilesBlock then one rebuild (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringOperations.cs:91–115). Brush RegisterUndo starts a gesture; tool deactivation/mouse leave/idle scene GUI ends and collapses it (Editor/ShipRoomBrushEditor.cs:54–69; Editor/ShipRoomBrush.cs:20–30; Editor/RoomAuthoringOperations.cs:21–35). Rebuild validates then Apply or Clear, records diagnostic, marks scene dirty and emits GenerationCompleted (Editor/RoomAuthoringOperations.cs:126–154). Save lifecycle deactivates/tags the occupancy mask without removing its cells (Editor/RoomAuthoringEditLifecycle.cs:22–34). Serialized room references/identity and Tilemap cells persist; persistence test saves/reopens and compares ID, asset GUID, cells and placements (Assets/_Project/Tests/Editor/RoomPersistenceTests.cs:97–115). Undo/Redo tests compare authored/generated/diagnostic snapshots (Assets/_Project/Tests/Editor/RoomUndoRedoTests.cs:15–26,74–79).

### What existing ownership and cleanup mechanisms distinguish generated content from painted occupancy and unrelated scene content, and how do rebuilds remove obsolete geometry without deleting unaffected authored cells?

Ownership checks reject duplicate IDs, shared occupancy/output, foreign output owners, ambiguous owner roots and nesting occupancy/output inside one another (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringCreation.cs:43–72). Safety additionally refuses generated roots containing other ownership roots or any referenced authored occupancy, including other loaded scenes (Editor/RoomAuthoringOperations.cs:74–85). Clear destroys every child under the verified output root using Undo, and Apply recreates content (Editor/RoomGeometryWriter.cs:10–22); authored map and unrelated room siblings are outside that root. Missing-output recovery is allowed only when no retained ambiguous ownership exists (Editor/RoomAuthoringCreation.cs:58–63; Editor/RoomAuthoringOperations.cs:129–138). Tests cover duplicate output ownership and foreign authored descendants (Assets/_Project/Tests/Editor/RoomOwnershipTests.cs:18,66,113,134).

### How do current boundary extraction and placement paths handle a single-cell erase, cutouts, concave corners, holes, disconnected painted regions, and empty occupancy, and where do they reject layouts or clear generated output?

Extractor deduplicates cells, sorts y/x, collects exposed cardinal edges into ordered contiguous runs and records convex vertices when both adjacent cardinal cells are absent (Assets/_Project/Features/World/RoomAuthoring/Geometry/RoomBoundaryExtractor.cs:12–46). Empty input returns empty arrays; nonempty IsRectangle is bounding area == cell count (same file:14,45). Geometry contains only Cells/Runs/ConvexCorners/Bounds/IsRectangle, without concave corner or loop/hole data (Geometry/RoomGeometry.cs:17–23). Thus exposed edges from cutouts/holes/disconnected regions can be extracted, but any non-full rectangle is rejected by placement, and failed rebuild clears generated output (Generation/RoomPlacementBuilder.cs:28–30; Editor/RoomAuthoringOperations.cs:140–143). Single-cell corner erase is explicitly tested as 47 retained cells, rectangle failure and empty output; empty occupancy succeeds even without style (Assets/_Project/Tests/Editor/RoomValidationTests.cs:13–34).

### When asset configuration or boundary placement is unresolved, how do current generation and validation paths distinguish valid placements from unresolved segments, remove stale geometry, and refresh issues after edits and Undo or Redo?

Validation returns the first safety, overlap, configuration or placement string; TryBuild may have accumulated placements before returning false, but RebuildCore only writes when valid and otherwise clears all owned output (Assets/_Project/Features/World/RoomAuthoring/Editor/RoomAuthoringValidator.cs:17–29; Generation/RoomPlacementBuilder.cs:33–57; Editor/RoomAuthoringOperations.cs:140–146). No current valid-versus-unresolved segment result model exists in RoomPlacement, which holds Geometry and a sprite list only (Generation/RoomPlacementBuilder.cs:16–20). Invalid-style tests assert zero output, preserved cells and full recovery after correction (Assets/_Project/Tests/Editor/RoomValidationTests.cs:42–70). Diagnostic changes are Undo-recorded, and Undo tests restore diagnostics with generated content (Editor/RoomAuthoringOperations.cs:149–154; Tests/Editor/RoomUndoRedoTests.cs:17,74–77). No custom Tilemap change or undoRedo subscription was found in the RoomAuthoring C# source; Inspector tells users to Validate/Rebuild after other-tool edits (Editor/ShipRoomAuthoringEditor.cs:29).
