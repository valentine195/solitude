# QRSPI Approach: floor-driven-room-authoring

## Context

The requested Phase 1 is editor tooling: select a style, paint room occupancy through the Tile Palette, and derive flooring, north wall faces, caps, and four rectangular-room corners in one deterministic pass. The authored region and stable room identity remain authoritative; generated architecture never feeds generation. Existing production scenes, gameplay composition, collision, doors, and art remain outside the change.

The 2026-10-19 clarification in `request.md` establishes intended source dimensions of **128×256 walls, 128×128 caps, and 64×64 floors**, superseding the earlier illustrative dimensions. It does not establish that current imports conform. The retained baseline is a **32×32 logical cell at 32 PPU**. A 128-pixel wall is consequently four logical cells wide, while a 64-pixel floor image covers two cells in each direction. A cap canvas's 128-pixel extent does not establish its structural repeat distance or visible thickness.

The tooling architecture can be selected now. A visually complete Standard demonstration cannot responsibly be promised until the asset family, density, alignment, and floor-coverage decisions below are resolved. No code, asset import change, or visual verification has occurred in this shaping pass.

## Candidate Approaches

### Option A: Room-specific brush with explicit generation transactions

**Shape.** Each room owns an explicit ID, a style asset, and a dedicated serialized occupancy Tilemap. A custom Tile Palette brush targets only the selected room's authoring map. Occupancy is a logical mask independent of floor imagery. The brush passes each completed operation to a room-scoped deterministic generator; an Inspector rebuild uses the same path. Box Fill/Erase are batches. The generator separates integer-cell boundaries and runs from style-dependent placement and Unity scene writing.

Use a generated floor Tilemap with an ordinary Tile or RuleTile and owned SpriteRenderers for large walls, caps, and corners. A floor rendering lattice may have a different visual repeat spacing from the logical occupancy lattice; this does not enlarge the authoritative 32-pixel grid. Explicit anchors, structural footprints, and pixel offsets account for padded art. Generated output ownership is explicit through references/markers, independent of hierarchy names. No runtime regeneration loop is needed.

**Fit and compatibility.** This follows the requested GridBrush workflow and makes the boundary of a batch explicit without depending on undocumented native Tilemap notifications. Separate room maps retain identity even for adjacent equal-style rooms. General cell occupancy/boundary extraction remains reusable while Phase 1's visual resolver rejects unsupported irregular perimeters or module widths. It does not require new SceneBindings branches or Domain/Application refactoring.

The authoring-only occupancy container can remain inactive outside editing, with editing visibility controlled by the tool, so it does not become a runtime floor candidate. SpriteRenderer architecture avoids the existing Tilemap-as-floor heuristic. The visual floor lattice must cover its represented surface semantically as well as visually: sparse 64-pixel tiles at two-cell anchor intervals on a unit-cell Tilemap would leave `HasTile` gaps. A dedicated visual Tilemap lattice matching the chosen floor footprint is preferable to that sparse representation, subject to the floor decision below.

**Complexity and operational behavior.** The custom brush/editor must coordinate room target selection and Undo for authored data plus owned generated content. That is more work than relying on the stock brush alone, but it makes a single operation's changes visible and testable. Undo/Redo should restore the recorded state as a unit; it should not rely on callback order to perform fresh unrecorded destructive rebuilds. Exact stroke grouping and generated-object restoration still need executable editor tests.

**Failure modes.** Direct edits with other tools can bypass the supported generation path. Restrict the advertised editing target/workflow, show out-of-date output clearly, and retain explicit Validate/Rebuild recovery. Failed visual resolution should preserve authored occupancy, identify the unsupported reason, and remove or hide obsolete owned output rather than presenting it as current. Empty occupancy should yield empty generated output. Overlapping room occupancy can be diagnosed without implementing shared-wall resolution. Preflight resolution before writing reduces partial-output risk; ownership limits recovery to the current room.

**Testing and migration.** Pure geometry and placement descriptions support focused deterministic tests; editor fixtures cover batch behavior, generation ownership, Undo/Redo, and save/reload. Native-pixel renders remain necessary for art alignment. A new isolated demo and reusable palette avoid converting existing rooms. Removing a demo room's owned output or rebuilding from its mask is a reversible local operation; existing room-builder assets retain their GUIDs and behavior.

### Option B: Stock brush with an occupancy-change observer

**Shape.** Retain the same per-room occupancy maps, explicit identity, geometry calculation, style assets, and owned visual outputs. Designers use Unity's ordinary Tile Palette brush. An editor observer watches occupancy changes, coalesces them, and invokes generation after each editing operation and Undo/Redo.

**Strengths.** The familiar default brush remains available and more direct Tilemap edits can trigger regeneration. The approach could eventually accommodate tools beyond the custom brush without separate integrations. The data and rendering separation are as strong as Option A if ownership and validation are retained.

**Costs and risks.** Research has not established the event timing required to distinguish a completed batch from intermediate writes, nor whether callbacks can be ordered reliably with Undo restoration. Coalescing notifications risks delayed stale previews, recursive notifications from generated maps, duplicate rebuilds, and splitting one gesture across Undo groups. Scope filters and deferred work add lifecycle concerns around scene reload, domain reload, destroyed targets, and multiple rooms. A broad scene scan or runtime update loop would conflict with the request.

**Testing and migration.** Besides Option A's geometry and rendering checks, this needs an editor event-order investigation and stress tests for event reentrancy, batching, Undo/Redo, scene opening, and queued rebuild cancellation. It offers a gentler default-brush experience, but a larger synchronization surface. Existing production scenes still need no migration; conversion from Option A could preserve occupancy/style data if this becomes justified later.

## Recommendation

Choose **Option A**, with selection **conditional on resolving asset readiness and the floor footprint policy before implementation is authorized**. It best matches the stated editor-first scope and makes batched edits, generation ownership, and Undo transactions explicit. Do not make Tilemap change notifications a Phase 1 dependency. They can be revisited after a narrowly scoped Research investigation if stock-brush interoperability becomes a requirement.

Prefer the mixed writer: editable occupancy and visible flooring use Tilemaps; architecture uses owned SpriteRenderers positioned from deterministic geometry. This accommodates tall/padded multi-cell art and avoids introducing more non-floor Tilemaps into existing runtime floor detection. Connected RuleTiles remain appropriate for the floor style or other compatible tile-based visuals, but should consume authored geometry rather than generate more authoritative geometry recursively. The old rectangle-boundary RuleTile is prior art, not a reusable occupancy solver.

Keep new feature-owned types/data and its authoring guide under `Assets/_Project/Features/World/RoomAuthoring`, Editor scripts in that feature's Editor assembly reference, reusable tiles/palette under `Assets/_Project/Art/Tiles`, tests under the existing Edit Mode owner, and the isolated demo outside production scenes/build entries. These are likely change owners, not an implementation sequence. No existing art, import metadata, gameplay composition, production scenes, or existing builder needs modification merely to establish the tool.

**Smallest proposed correction for the dimensions conflict:** preserve the 32-pixel logical grid and native scale. Treat the clarified 64-pixel floor as a two-by-two-cell visual module, and the 128-pixel north wall as a four-cell-wide module. For Phase 1, recommend allowing visual completion only when the rectangle can be exactly covered by the configured native floor and structural modules; preserve arbitrary logical occupancy but report unsupported interim shapes without stale architecture. An 8×6 mask can hold twelve 64×64 floor modules and two 128-pixel north-wall modules at 32 PPU. This is dimensional arithmetic, not evidence that current art assembles. It adds a floor-coverage restriction that needs an explicit human decision; do not silently crop, scale, overlap, reslice artwork, or replace the logical grid with a coarser one. Cap repeat distances and corner reservations require actual alignment evidence and cannot be inferred from the clarified canvas sizes.

Changing existing imports to meet these dimensions/32 PPU is not part of the selected tooling approach. If the chosen Standard family still uses 100/128 PPU, asset preparation requires its own explicit scope decision. Do not hide that mismatch with transforms, a rescaled room root, or a different logical grid.
