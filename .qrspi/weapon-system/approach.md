# QRSPI Approach: weapon-system

## Context

The requested outcome is a newly started player equipped with a maintenance wrench who can miss, swing into range, receive restrained hit feedback, and defeat SEC-0. The architectural foundation must support reusable item actions and general gameplay-tag queries while keeping combat, environmental interaction, and existing consumable behavior separate. Only melee is implemented now; repair, backgrounds, additional playable weapons, and an ability/effect framework remain outside scope.

This proposal uses the current `request.md`, its SEC-0 clarification, `queries.md`, and existing `research.md`. No background or prior approach was supplied. Research's historical question about the introductory enemy is answered by the request clarification and is resolved.

A material distinction from the original brief is that SEC-0 currently supplies a nonlethal stun encounter, not a damageable enemy with an existing death/drop system. Adding the minimum incoming-health and defeat lifecycle is necessary to deliver the approved outcome. It should not become an AI redesign or a new loot system.

## Candidate Approaches

### Option A: Selected-hotbar equipment with a small actor action runtime

Treat the selected hotbar slot as the equipped item for this slice. Add a small equipped-item adapter over the existing reader and selection, then route primary-action requests to the selected item's configured primary action. Keep item ownership in containers and retain the current Use and Interact routes. ItemDefinition gains additive tags/action references and optional held presentation; existing identity, consumable and inventory fields remain intact.

ScriptableObjects author tags, actions, wrench configuration and starting loadout. Startup compilation validates these assets and builds read-only runtime views. Each actor owns its execution phase, elapsed time, captured item binding, facing, target-hit set and movement/feedback cleanup. A small reusable action execution boundary lets a future action provide different behavior without editing movement or the melee implementation. The wrench is an item asset using MeleeAttackAction configuration, not a wrench subclass or a tag-selected behavior branch.

A centralized tag registry owns stable serialized definitions and hierarchy. Item/entity sets and queries resolve against that registry once; frequent checks use resolved identities and ancestor information rather than reparsing dotted strings. Authoring uses inspectable references; stable identity is distinct from display/hierarchy labels and from compact runtime indices. Runtime indices are local to a compiled registry and are not saved as durable identities. Validation rejects missing references, duplicate identities/names, invalid hierarchy and malformed definitions. Ordinary tag sets can be empty; an empty eligibility query imposes no tag restriction, preserving untagged damageable recipients. Exact and hierarchical matching remain deliberate query choices. Required, any and excluded groups are general rules, not combat-only predicates. The later spec defines the full truth table and validation behavior.

The melee behavior supplies directional geometry, while a shared damage-delivery boundary accepts a damage event and resolves an authoritative recipient. Player recipients adapt to existing Damage; SEC-0 receives a minimal health owner and defeat adapter. Feedback follows accepted damage, with optional presentation and supported displacement separated from damage calculation.

**Strengths.** Fits existing ownership, HUD, input policy and save identity. Adds only the state needed to perform an item action. Reuses item/container transactions without extending them into an equipment framework. Pure tag and timing logic can be tested independently; physics and composition can use existing PlayMode patterns. A different test item/action configuration demonstrates reuse without controller changes.

**Costs and risks.** Selecting a consumable changes the equipped item; there is no independent “wrench stays in hand while a different hotbar item is selected” model. The adapter must watch selected-slot contents and ownership revisions, not just index changes. Fresh-run equip ordering must follow the existing selection reset. Adding primary input requires authored binding and input tests. New SEC-0 health/death behavior needs explicit lifecycle integration because no such system exists today.

**Migration and rollback.** Existing items default to empty tags/no primary action; their stacking, IDs, saves and consumables continue through existing catalogs. No dedicated equipment save schema is needed for this slice. This does not imply zero save-format changes: durable loadout initialization may reuse existing lifecycle evidence or need a narrowly scoped additive marker, to be settled in Spec. New-run auto-equip is explicit; this option does not promise persisted equipped selection on resume. Removing the new feature composition/action configuration restores existing input and container behavior without rewriting item IDs. Saves that contain the wrench still require its definition to remain available, as with any saved item.

### Option B: Independent equipped-item state backed by existing inventory

Introduce an actor equipment coordinator with its own equipped binding, independent of hotbar selection. Inventory still owns the item; the equipment coordinator tracks which owned slot/item is equipped and validates that binding through transfers, replacement, restore and handoff. Primary input uses the equipped item while hotbar Use can continue targeting a different selected consumable. Tags, action definitions, action runtime and shared damage delivery can otherwise follow the same small design as Option A.

**Strengths.** Supports a familiar persistent held weapon alongside separately selected consumables. Makes an explicit equipment boundary available for later multiple equipment positions. Ownership remains in the existing inventory rather than a duplicate storage system.

**Costs and risks.** Requires an equip/unequip selection policy or gesture, separate HUD state, and decisions about what happens when the equipped item moves between slots/containers. Durable equipped references introduce save/resume and succession considerations beyond today's selected-index model. Without unique per-instance item identity, tracking an item across arbitrary moves is especially delicate; slot bindings can be safely invalidated but do not magically follow identical items. These concerns are meaningful product behavior, not boilerplate. Testing must cover two independent selections, ownership loss, stale references and restoration.

**Migration and rollback.** Existing saves need a default for the new equipment state if it is persisted. Keeping it session-only avoids that migration but loses its primary persistence benefit. Reverting requires removing the extra state/UI/input path and deciding how equipped references return to ordinary selection behavior. More coordination surface is introduced before the current slice needs it.

| Concern | Option A | Option B |
| --- | --- | --- |
| Immediate wrench outcome | Direct fit through selected slot | Achievable with extra equip policy |
| Existing HUD/input compatibility | Reuses active-slot display; adds primary route | Needs distinct equipment display/control |
| Weapon plus independently selected consumable | Requires switching selection | Naturally supported |
| Mutable state and ownership | Execution state plus derived equipped view | Execution state plus separate equipment state |
| Save/succession integration | Existing container persistence; explicit fresh-run selection | Additional equipment restoration semantics |
| Principal failure mode | Missing occupied-slot replacement invalidation | Stale independent ownership/equipped binding |
| Verification burden | Selected-slot lifecycle and action/physics integration | Same action checks plus two-selection coordination |

A controller switch on item IDs/tags and a full ability/effect framework are not viable alternatives: the former conflicts with reusable behavior ownership, and the latter exceeds the explicit scope. Neither is needed to deliver the requested extension points.

## Recommendation

Choose **Option A**. It supplies a useful foundation while building on the project's actual equipment mechanism. Independent weapon/consumable selection is a legitimate later product choice, but the present request does not justify introducing that second state machine now.

The recommended architecture has these responsibilities and boundaries. Names describe ownership, not frozen class names, signatures or implementation steps.

**Tags and authoring.** Keep general registry/set/query rules in Domain and Unity authoring/inspection/compilation in the runtime/editor layers. Prefer centrally registered tag-definition assets with stable identity and explicit parent relationships, compiled into an immutable registry snapshot. Dotted names remain readable authoring labels; changing a label must not silently retarget serialized assignments. Items and optional entity tag components use the same registry. Action damage tags are authored on the action/event configuration; the wrench's Item.Tool classification does not automatically become a damage property. The wrench asset carries Item.Weapon, Item.Tool, Item.Improvised, Weapon.Melee, Damage.Blunt and Tool.Mechanical, while its melee damage event explicitly carries Damage.Blunt. No runtime rule maps those tags to MeleeAttackAction. Repair remains a future separate action, not an inferred behavior of Tool.Mechanical.

**Equipment, input and facing.** The equipped adapter resolves the active slot into its definition/actions and exposes that state to presentation and action requests. Capture an ownership/revision-aware binding for the swing; invalidate it on relevant slot mutation, selection change, owner replacement/unavailability or lifecycle release. There is no item lock and no new inventory owner. Primary input is a separate host route following existing freshness/UI/policy rules; F/gamepad Use and environmental Interact keep their current responsibilities. A small actor facing source retains the last meaningful movement direction and an authored initial direction, using existing movement conventions. Capture swing direction at action start for a readable committed arc. Movement only knows generic scoped restrictions: a speed factor lease can provide modest wrench slowdown while existing full blocks retain precedence. It never examines tags or action types.

**Action lifetime.** Shared action configuration describes eligibility and action-specific behavior. A generic actor-owned runner owns the current execution, checks actor/equipment availability, and ensures interruption and cleanup. The melee execution owns its Idle, Windup, Active and Recovery phases and timing. Future non-melee executions can have different lifecycles without adopting melee phases or changing the runner, movement or melee implementation. This is one reusable execution boundary, not an effect graph, scheduler network or catalog of speculative action types. Actor availability includes living vitals, active lifecycle and stun/incapacitation. Death, unequip, interruption and release cancel execution and release all owned resources idempotently. Pause freezes gameplay progress and prevents requests; scene/owner invalidation cancels rather than carrying a swing into a different actor or scene. Resume requires fresh input and recovery cannot be bypassed by repeat requests. Melee timing uses elapsed scaled gameplay time with phase-boundary handling so an update crossing the short active interval still performs the intended active evaluation. Physics sampling remains tied to observed world state; timing independence is not a claim of continuous reconstruction of arbitrary motion between frames.

**Melee geometry and damage.** Use reusable Physics2D query buffers for a broad nearby-collider candidate set, followed by directional range/arc and obstruction evaluation. Resolve colliders to a stable recipient owner; deduplicate across colliders and active samples per swing. Exclude actor hierarchy before target selection. Keep tag-based eligibility optional and separate from geometric reachability. Use explicit filters and solid geometry for blockers, ignoring self and the target's own shapes when checking obstruction. Authoring/verification must establish real blocking colliders where the encounter requires them. Buffer saturation should produce a visible diagnostic and conservative outcome rather than silently claiming complete targeting; capacity is an implementation tuning concern.

The damage boundary carries amount, attacker/target, source item/action, impact position/direction and event damage tags. Calculation produces an amount independently of hit detection; recipient adaptation performs the authoritative mutation and reports whether it applied. Do not introduce speculative resistance/modifier pipelines. The existing player vitals Damage path remains the player health mutation. SEC-0 gets only the health state needed to receive damage and become defeated; do not attach hunger/recovery vitals to robots. A provisional authored maximum of 40 health makes the initial 10-damage wrench a four-hit encounter, subject to play evaluation. This is new enemy configuration, not a change to an existing health balance.

**SEC-0 response and feedback.** Defeat must stop SEC-0's current movement, windup/fire and pulse resources and remove it from live targeting/physics participation through its established lifecycle. Extend that lifecycle minimally, retaining nonlethal outgoing stun and existing perception/navigation rules. There are no existing drops to migrate or invent. A focused SEC-0 presentation adapter owns brief flash and restrained, collision-aware knockback integrated with its kinematic movement; unsupported recipients can decline knockback. Avoid a second component racing the bot's Rigidbody2D movement. Accepted hits can emit optional contact effect/audio; swing presentation follows gameplay phases without animation events owning damage. Missing assets remain safe. Compact placeholder wrench/swing art is sufficient.

**Starting loadout and presentation.** A configuration referenced by runtime setup names the starting wrench grant and selected slot. Apply it at the explicit first-run initialization boundary after registered containers exist, and establish selection after awakening's reset. Use the existing command/initialization machinery and retain durable new-run initialization evidence so save/resume, scene arrival, retry or successor awakening cannot grant duplicates. Reuse existing durable lifecycle evidence if it safely distinguishes successful loadout initialization; otherwise a narrowly scoped additive save marker may be necessary. Spec must settle that choice; avoiding a separate equipment save schema is not a promise that all save formats remain untouched. A failed grant must not be mistaken for a completed loadout. Disposable demos opt into their configured fixture separately. Do not automatically give every replacement survivor a wrench or refresh a resumed expedition. Background-specific loadouts can later choose another configuration without implementing background rules. Reuse the selected hotbar icon/highlight for equipped information, adding a compact name/action hint only if the current HUD can accommodate it; no equipment screen is needed.

**Likely ownership and affected areas.** Pure tags, action timing/eligibility and minimal damage values belong in Domain; selected-item execution coordination belongs in Application. Core owns primary input, scene/runtime-config wiring and first-run lifecycle integration. Shared Unity hit resolution/presentation adapters belong in Systems where reused. Item/action/loadout assets stay with Features/Items; the actor integration belongs with Features/Player; SEC-0 health/defeat integration stays with Features/Npcs/Sec0. Existing movement, item compilation/validation, hotbar presentation, scene composition and the SEC-0 demo are expected integration surfaces. Preserve current assembly and GUID boundaries. Architecture documentation and review evidence stay outside imported Assets according to the project structure.

Verification should combine pure tag/query and boundary-crossing timer tests with actual Physics2D, input, ownership-change and lifecycle scenarios. In particular, exercise occupied-slot replacement, shared definitions across two actors, interruption during each phase, low-frame-rate active-window crossings, multiple colliders/targets and solid cover. Existing consumable, movement, vitals, SEC-0 stun, container and room-generation suites remain relevant regression evidence. Extend the existing SEC-0 disposable encounter for the equipped wrench demonstration rather than introducing another enemy or a room-generation workflow. No validation has run at this proposal stage; these are verification concerns for specification/planning, not claimed results.

## Decision

Approved: Option A — selected-hotbar equipment with a small actor action runtime. The human answered “Yes” to approval of Option A and proceeding to Spec. The selected approach reuses current item ownership, hotbar selection and presentation while avoiding independent equipment state for this slice.
